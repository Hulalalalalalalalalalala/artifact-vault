# Artifact Vault

Artifact Vault is a small Go command-line service for storing named files by content digest. It is the initial product baseline for a file and artifact storage system.

## Build and test

```bash
go test ./...
go build ./cmd/artifact-vault
```

## Usage

```bash
artifact-vault init --root ./vault
artifact-vault put --root ./vault --name releases/app.bin --file ./app.bin
artifact-vault list --root ./vault
artifact-vault get --root ./vault --name releases/app.bin --output ./restored.bin
artifact-vault verify --root ./vault
```

`put` stages the upload in a temporary file inside the repository while computing its size and SHA-256, then either installs it as a new content object or reuses the object already stored under the same digest. A successful put means the object behind the name's digest is verifiably complete: an existing object is reused only when it is a regular file whose full contents can be read and whose actual size and SHA-256 equal the upload's. A truncated or rewritten object (including a same-size object with different bytes), a symlink (followed or dangling), a directory, or an unreadable path fails the upload; the damaged object is never repaired by overwriting it, and the name mapping, existing objects, and snapshots are left unchanged, with the staged upload removed. Reuse never copies, rewrites, or re-permissions the healthy object, so any number of names — current or snapshot-only — can share one object. Errors name the upload, the digest, and the reason, distinguishing size mismatch, checksum mismatch, a non-regular-file path, and inspection or read failures.

Both adding a new name and overwriting an existing one presuppose the whole current name mapping. Before the input is read, the current `index.json` must satisfy exactly the strict rules `verify` and `snapshot create` apply: one complete JSON object with an explicitly present, object-valued `entries` mapping — a genuine `{"entries": {}}` is a legitimate empty repository and accepts an empty or a normal file, while a bare `null`, an empty `{}`, a missing or `null` entries field, a non-object entries value, a truncated document, trailing content after the object, or any duplicate key at any level (a repeated `entries` field, the same artifact name appearing twice, including one written directly and one through Unicode escapes, or a repeated field inside one record) is corruption. Every existing record must additionally satisfy the current record rules: the mapping key equals the recorded name, the name is legal, the digest is 64 lowercase-hex characters, and the size is non-negative. A single bad record fails the whole upload even when it is unrelated to the name being uploaded; the mapping is never treated as empty, rewritten around the damage, or filtered into a partial save. Failures are reported as `cannot store <name>: current index is corrupt: …` (or `current index cannot be read: …` when the index bytes themselves cannot be read), with the duplicated key or offending artifact named; this stays distinct from a failure to read the input file and from a damaged existing content object. On such a failure the command prints no `stored` success line, the Go API returns no usable entry, the original index bytes, all snapshots, and all content objects are untouched, no object for the new digest is installed, and no staged temporary file remains. A first upload still auto-initializes the repository; a successful overwrite replaces only that name's record, leaving every other record's digest, size, and creation time unchanged. Content checks stay limited to the object this upload needs, and snapshot restore's ability to repair a corrupted index is unchanged.

`get` only delivers a file when the recorded name exists, the index and record are intact, and the stored object's actual size and SHA-256 match the record. The object is streamed and hashed into a temporary file beside the output; the output is replaced only after the complete, verified bytes are flushed, so a failed download leaves an existing output byte-for-byte unchanged and a missing output absent. Empty objects download normally, and large objects are streamed without buffering in memory.

The output must be safe: its parent directory must exist (it is never created), it must not be inside the repository — including a not-yet-created path or a path reached through a symlinked parent — and an existing output must be a regular file outside the repository that is not a hard link to any index, snapshot, lock, or content object. Symlinks, directories, and other non-regular files are refused. Errors distinguish a missing name, a corrupt record, a corrupt object, and an unsafe or unwritable output, and name the relevant artifact or output path. A download takes the shared repository lock, so it always observes one complete pre- or post-operation version and can never be interrupted mid-collection.

`verify` first requires the current name mapping itself to be complete and unambiguous: the index must be one complete JSON object with an explicitly present `entries` mapping (a genuine `"entries": {}` is a legitimate empty repository; `null`, a missing or null `entries`, an array, truncated input, trailing content, or any duplicate key — including a name repeated through Unicode escapes — is corruption), and every record must be keyed by its recorded name with a legal name, a 64-character lowercase-hex digest, and a non-negative size. A single malformed record fails the whole pass and is reported as index corruption, naming the duplicated key or the offending mapping name, before any object is read. Only then does verify check every entry against its content object — the object must exist and its actual size and SHA-256 must match the record — and print `verified N artifacts`, where N counts names (two names sharing one digest count as two). The whole pass, from reading the mapping to the last object check, runs under one shared repository lock: an overwrite, snapshot restore, import, or gc in another process either completes before the pass starts (and the pass observes the completed state) or waits until the pass ends, so a healthy repository is never reported as missing an object that a concurrent gc just collected. The lock is shared, so lists, downloads, and other verifies proceed alongside it. A missing object, a size or checksum mismatch, or a read failure is reported with the artifact name and no success line is printed; verify never rewrites the mapping, snapshots, or objects and never repairs damaged content.

## Snapshots

Snapshots record the complete name mapping (name, digest, size, creation time of every entry) so the repository can be rolled back before overwriting artifacts. They reference the existing content objects; no artifact bytes are copied.

```bash
artifact-vault snapshot create --root ./vault --name before-release
artifact-vault snapshot list --root ./vault
artifact-vault snapshot restore --root ./vault --name before-release
```

`snapshot list` prints one `name<TAB>entry-count` line per snapshot, sorted by the complete snapshot name — a multi-level snapshot prints as `releases/stable`, never just `stable`. The entry count is the number of records in the snapshot's entries mapping, so one content object referenced by two artifact names counts as two entries, and a genuine `"entries": {}` snapshot lists with zero entries. An initialized repository with no snapshots yet (its `snapshots/` directory does not exist) succeeds with an empty listing.

`snapshot create` first requires the current name mapping itself to be complete and unambiguous, and only then records the snapshot under the selected name. The current `index.json` must be exactly one complete JSON object with an explicitly present, object-valued `entries` mapping: a genuine `{"entries": {}}` is a legitimate empty repository and creates, lists, and restores as a zero-entry snapshot, but a bare `null`, an empty `{}`, a missing or `null` entries field, a non-object entries value (array, string, number), a truncated document, or trailing content after the object is rejected. Any duplicate JSON key at any level is rejected too — a repeated `entries` field, the same artifact name appearing twice (including a name written directly and again through Unicode escapes), or a repeated field inside one entry — rather than silently keeping only the last occurrence. Every entry must additionally satisfy the existing record rules: the mapping key equals the recorded name, the name is legal, the digest is 64 lowercase-hex characters, and the size is non-negative. Validation is all-or-nothing and happens before anything is written: one bad record rejects the entire operation; bad entries are never skipped to leave a seemingly usable partial snapshot.

Failures name the snapshot being created and the concrete reason the current index is unusable (`cannot create snapshot <name>: current index is corrupt: …`), with the duplicated key or offending artifact name identified; this stays distinct from an illegal snapshot name and from a same-named snapshot already existing (`snapshot <name> already exists`, which still refuses to overwrite). On failure the command prints no success line, the Go API returns no usable snapshot, no new snapshot record appears, and the original index bytes, existing snapshots, and content objects are left untouched (the record is staged via a temporary file plus rename). A successful snapshot preserves every name, digest, size, and creation time exactly; several names sharing one digest each keep their own record. Creation still records metadata only and references existing content objects — it never copies artifact bytes — and restore and export continue to verify the referenced content under their existing rules. Multi-level snapshot names are supported, the command line and the Go API apply exactly the same validation, and a successful create keeps printing `snapshot <name> created with <entries> entries`.

A snapshot is shown only after its record proves complete and valid under the same rules restore enforces: the file must be a regular file (never a symlink) holding exactly one JSON object with no duplicate or unknown top-level fields and no trailing content, a recorded `name` equal to the snapshot's filing name in full, and an `entries` field that is present and a JSON object — a bare `null`, an empty `{}`, a missing or `null` entries field, a non-object entries value, a name mismatch, or an artifact record that fails the existing name/digest/non-negative-size/key-matches-name rules is corruption, never a snapshot to display. Any single damaged or unreadable record fails the whole command: the error names the complete snapshot and the reason, the Go API returns no partial list, and no earlier snapshot lines are printed. Listing reads only snapshot metadata — it never reads or verifies content objects and does not depend on the current name mapping being healthy — and never modifies the mapping, snapshot records, or objects. Temporary files and other non-`.json` files in `snapshots/` are ignored.

`snapshot restore` replaces the current mapping only after the selected record proves complete and healthy: it must be a single JSON object containing `name` and `entries`, the recorded `name` must equal the selected snapshot name in full (restoring `releases/stable` rejects a record that says only `stable` or names another snapshot), and `entries` must be present and an object — a missing field, a `null`, a non-object value, or a record that is just `null` or `{}` is corruption rather than an empty snapshot (though a genuine `"entries": {}` restores to an empty list). Every referenced object is re-checked for existence, size, and SHA-256 before the current mapping is atomically replaced. Failures name the selected snapshot and say whether the record is missing its entries mapping, has a mismatching name, or is malformed — distinct from a snapshot that does not exist — and the command fails without printing a success line. Any failure leaves the current mapping (including its original bytes when it was already corrupted), the snapshot record, and every object untouched; restore never reads a healthy current index as a precondition, so it repairs a corrupted `index.json` as long as the snapshot and its objects are intact. The command line and the Go API apply exactly the same rules.

## Moving snapshots to another machine

A snapshot package carries one complete snapshot, together with the content objects it needs, so it can be copied to and restored from a different repository.

```bash
artifact-vault snapshot export --root ./vault --name before-release --output ./before-release.vaultpkg
artifact-vault snapshot export --root ./vault --name after-release --base before-release --output ./after-release.vaultpkg
artifact-vault snapshot import --root ./other-vault --file ./before-release.vaultpkg
artifact-vault snapshot restore --root ./other-vault --name before-release
```

The destination repository must already be initialized. `snapshot export` writes a portable package (`--output`, atomically) containing the target snapshot's full entry metadata; a digest shared by several entries is carried once. Export re-verifies the size and SHA-256 of every object the snapshot references and never leaves a partial output file behind on failure.

The export output is held to the same safety rules as a `get` download, for both full and incremental packages (the command line and the Go API behave identically): the source repository must already exist and be initialized (export never creates one); the output must lie outside the source repository judged on actual locations — this covers paths that do not exist yet, a repository root specified through a symlink, and any symlinked parent that leads back into the repository, while a relative `..` path cannot escape the check and an unrelated directory sharing the repository's name prefix stays usable. The output's parent directory must already exist and be accessible (it is never created), although a symlinked parent that resolves to a normal directory outside the repository is fine. An existing output must be a regular file: symlinks (even dangling ones), directories, and other special files are refused and never replaced. A file outside the repository that is a hard link to the index, any snapshot record, the lock file, or any content object — including objects the exported snapshot does not reference — is also refused. The package is staged in the pinned parent directory and committed through its file descriptor, with the containment, file-type, and hard-link checks repeated immediately before the rename, so a parent replaced by a symlink to the repository during the export fails as an unsafe output and can never put the package on a repository file. Unsafe-output errors name the output path and the reason; missing/corrupt snapshots and missing/mismatching objects are still reported by snapshot name or object digest. On any failure the existing output (its contents and permissions), the repository's mapping, snapshots, objects, and lock are all left unchanged; an interrupted export leaves at most a temporary file, and retrying succeeds.

With `--base <snapshot>` the package is incremental: it still records the target snapshot's complete mapping but only carries objects the base snapshot does not reference. Importing such a package requires the destination to already contain a snapshot with the base name and byte-identical entry metadata, with every omitted object present and intact; a same-named snapshot with different metadata, or objects that merely happen to share digests, is not a substitute for the base. A package without a base is self-contained and can be imported into an empty repository.

Every artifact record in the package's target snapshot must name the exact byte count of the content its digest identifies. This is checked independently for each name — one object shared by several names must be sized correctly by all of them, not just one — and it applies to the objects a delta omits too: even when the destination holds a matching, healthy base snapshot, a target record that keeps the base digest but declares a different size is a corrupt record and rejects the whole package. Zero-byte content with a size-0 record and genuinely empty snapshots remain valid. The package format is unchanged, so full and incremental packages produced by existing exports stay compatible and shared objects continue to be reused under the existing rules.

Import only adds the package's snapshot and any missing objects; it never changes the current name mapping or any existing snapshot or object. Healthy objects already present in the destination (including in an empty target initialized first) are reused; re-importing a package whose snapshot is already present with identical metadata succeeds without adding another copy, while a same-named snapshot with different metadata is refused. Afterwards `snapshot restore` applies the imported mapping, and imported content is protected from `gc` exactly like any snapshot-referenced object. All validation — including every target record's size matching its content — completes before anything is written: a carried mismatch is rejected while the package is read, and an omitted-object mismatch is measured from the destination while holding the lock, so no object is staged first and refused afterwards. On any failure — unknown package version, illegal names or digests, negative sizes, duplicate entries, a target record whose size disagrees with the actual bytes its digest identifies, missing or mismatching content, or a damaged destination object — the command fails (the Go API returns an error and no usable result) without printing the import success line, and the repository gains no content object, no target snapshot, and no leftover temporary file: the current name mapping, every saved snapshot, and the bytes and permissions of every existing object are unchanged, even when the package also carried other correct new objects. Such a size failure names the target snapshot, the artifact whose record is wrong, the content digest, the recorded size, and the actual byte count, so record corruption is distinguishable from a content checksum failure. An interrupted import (a crash or write error after an object landed but before the snapshot published) leaves at most unreferenced complete objects that the next `gc` clears and a retry completes.

Export prints `exported snapshot <name> with <entries> entries, <objects> objects`; import prints `imported snapshot <name> with <entries> entries, <new-objects> new objects`.

Objects are stored beneath `objects/` by SHA-256 digest. `index.json` maps logical names to immutable object metadata, and `snapshots/` holds one JSON record per snapshot. Writes use temporary files followed by rename so interrupted writes do not expose partial objects, indexes, or snapshots. All mutating operations (`init`, `put`, `snapshot create`, `snapshot restore`, `snapshot import`, `gc`) are serialized across processes with an `flock` on `<root>/.lock`, which is released automatically if a process dies mid-operation. `snapshot export` also takes the exclusive lock so the verified snapshot and its objects cannot change or be collected mid-export.

## Garbage collection

```bash
artifact-vault gc --root ./vault --dry-run
artifact-vault gc --root ./vault
```

`gc` deletes content objects that neither the current name mapping nor any saved snapshot still references — for example old versions left behind by overwritten uploads or objects orphaned by a snapshot restore. Objects referenced only by a snapshot (including snapshots with multi-level names) are kept. `--dry-run` deletes nothing and prints one `digest<TAB>size-in-bytes` line per candidate, sorted by digest, followed by a `total N objects, M bytes` summary; a real run prints `deleted N objects, M bytes`. Only regular files directly inside `objects/` whose names are valid digests are eligible; temp files, other names, subdirectories, and symlinks are left untouched, and the index and snapshots are never rewritten.

The pass runs under the exclusive repository lock, so it always observes a complete state and never collects an object while an upload, download, verify, or snapshot operation is in flight. Any unreadable or malformed reference (corrupt index or snapshot, invalid entry, snapshot name not matching its location, symlinks in `snapshots/`, an `objects/` path that is a symlink or unreadable) aborts the pass before anything is deleted. If a deletion fails mid-pass the command stops, reports the failed object and what was already deleted, and leaves the remaining candidates for the next run.

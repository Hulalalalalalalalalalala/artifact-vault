# trustpeek

离线环境下快速查看本地 X.509 证书信息的小工具。不联网、不做信任验证，只读取并展示证书本身携带的内容。

## 构建与运行

构建依赖（均为常规公开工具，离线即可完成）：

- CMake 3.20 或更新版本；
- 支持 C++20 的 C++ 编译器；
- OpenSSL 的 Crypto 库（含开发头文件，链接 `libcrypto`）。

```sh
cmake -S . -B build
cmake --build build
```

构建默认启用 CTest，并会顺带在构建树中**离线准备回归检查所需的证书样本**（`build/tests/fixtures/`）：随仓库只提交 PEM 样本，这一步用 POSIX shell 与 coreutils（`base64` 等）把每张证书 PEM 块的正文逐字节解码为同名 DER，不生成密钥、不重新签发、不联网，也不调用 Python 或系统信任库。样本准备失败（PEM 缺失、不可读或正文无法完整解码）会让构建直接报错并指出具体文件与原因，不会留下空 DER。

查看版本：

```sh
./build/trustpeek --version
```

输出：

```text
trustpeek 0.1.0
```

## 检查证书

```sh
./build/trustpeek inspect <文件路径>
```

示例：

```sh
./build/trustpeek inspect ./cert.pem
```

```text
Encoding: PEM
Subject: C=CN, O=示例科技有限公司, OU=研发部, CN=中文示例证书
Issuer: C=CN, O=示例科技有限公司, OU=研发部, CN=中文示例证书
Not Before: 2026-10-04T16:40:27Z
Not After: 2036-10-01T16:40:27Z
SHA-256 Fingerprint: 9D:B7:65:F9:94:07:DB:F9:93:4E:29:FB:AA:FD:A1:F8:EE:54:9A:EF:4E:E2:80:C6:47:55:B5:58:00:F5:74:23
Note: this output displays certificate information only; reading the file successfully does not verify the signature or establish trust.
```

路径包含空格时加引号即可：

```sh
./build/trustpeek inspect "dir with space/my cert.pem"
```

### 输出字段

| 字段 | 含义 |
| --- | --- |
| `Encoding` | 文件的**实际**编码，`PEM` 或 `DER`，由文件内容决定 |
| `Subject` | 证书主体名称，保留名称中的全部属性（不只显示通用名 CN） |
| `Issuer` | 颁发者名称，同样保留全部属性 |
| `Not Before` | 有效期开始时间，UTC 表示并以 `Z` 结尾 |
| `Not After` | 有效期结束时间，UTC 表示并以 `Z` 结尾 |
| `SHA-256 Fingerprint` | 证书 DER 编码的 SHA-256 指纹，大写十六进制、冒号分隔字节 |

- 名称中的中文等非 ASCII 内容以 UTF-8 输出；未知属性 OID 以点分形式（如 `2.5.4.5=...`）显示。名称值无论是 UTF8String、BMPString（每个字符两个字节）还是 UniversalString（每个字符四个字节）编码，都转换成相同的 UTF-8 文字：BMPString/UniversalString 为表示普通字符而包含的零字节既不会截断名称，也不会显示成转义；只有名称里**真实存在的零字符**才显示为 `\00`。值中小于十六进制 20 的字符（换行、回车、制表符、零字节等）显示为反斜杠加两位大写十六进制（如 `\0A`），因此名称里的控制字符不会改变信息行的结构。
- 时间一律使用带 `Z` 的 UTC 时间，因此同一证书在任何本地时区下输出都相同。
- 指纹针对证书的 DER 编码计算。同一证书分别保存为 PEM 和 DER 时，除 `Encoding` 外的所有字段完全一致。

## 支持的输入范围

- 一次只检查**一个完整的 X.509 证书**，接受 PEM 或 DER 编码。
- 输入路径必须指向一个**普通文件**（允许是符号链接，以其**最终指向的目标**为准）：
  - 符号链接指向可读普通文件时，与直接检查该文件的结果一致（也支持多级链接）；
  - 链接指向目录或下述特殊文件时，按目标的实际类型报告读取失败；
  - 链接目标不存在或没有读取权限，同样报告读取失败并说明实际原因（如 `No such file or directory`、`Permission denied`）。
  - 上述诊断中的路径一律保留用户传入的链接路径本身。
- 以下**特殊文件一律不读取、按读取失败拒绝**（退出码 1），诊断会说明目标不是可接受的普通文件：
  - 命名管道（FIFO）：无论有没有其他进程打开、写入或关闭管道，即使管道准备发送的是一份完整的 PEM 证书，也只按文件类型拒绝，命令不会等待写入者；
  - 字符设备与块设备：例如 `/dev/null` 会立即返回空内容，此时报告的是读取失败，**不会**被解释成“空证书”；
  - 本地套接字（Unix domain socket）；
  - 目录。
- 实际格式根据**文件内容**判断，与扩展名无关。例如把 PEM 文件改名为 `cert.der`，仍会报告 `Encoding: PEM`。
- PEM 证书块前后允许空白（空格、制表符、空行、CRLF）：空白可以独占行，也可以紧贴开始/结束标记，文件末尾不必再有换行；块内部的格式要求不变。
- 以下情况一律作为证书格式错误拒绝（退出码 1）：
  - 空文件或仅含空白；
  - 损坏、截断的数据；
  - 名称属性值的字符串编码不完整（例如 BMPString 内容长度为奇数，或 UniversalString 内容长度不是四字节的整数倍）；
  - 只包含公钥、私钥或其他非证书内容；
  - PEM 中出现第二个证书块或其他非空白内容；
  - 单个 PEM 块的 Base64 正文能完整解码，但解码结果并非**恰好**一张证书（例如完整证书之后还带零字节，或又拼接了一张完整证书——即使与第一张完全相同也不允许只显示第一张而忽略尾部）；
  - DER 证书之后存在多余字节。
- 文件不存在、不可读（如权限不足）、指向目录或上述特殊文件，或读取普通文件内容时发生系统错误时，一律报告读取失败（`failed to read file`，并带具体原因），与证书格式错误区分开；只有路径确认为可读普通文件、且完整读到文件末尾后才判断内容是否为证书。因此：
  - 诊断提示目标不是普通文件 / 是目录 / 是管道等时，应**更换输入路径**；
  - 诊断为 `invalid certificate` 时，路径本身没有问题，应**检查证书文件内容**。

## 查看信息不等于信任判断

`inspect` 只展示证书“写了什么”，**不判断证书是否可信**。具体来说：

- 不验证证书上的签名，也不验证颁发链；
- 不查询吊销状态（CRL/OCSP），不检查系统信任库；
- 证书已经过期、尚未生效，或者是自签名证书，只要能完整读取就照常显示并返回 0；
- 证书上的签名即使已经失效（例如证书内容在签发后被改动，签名验证不再通过），只要仍是一张结构完整的 X.509 证书，同样照常显示并返回 0——签名失效不是格式损坏，读取成功也不代表签名可信。

因此读取成功只代表文件是一个结构完整的 X.509 证书，不代表其签名有效或应当被信任。输出末尾的 Note 行会持续提醒这一区别。

## 退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功输出证书信息（过期、未生效、自签名也返回 0） |
| 1 | 文件无法读取（不存在、无权限、路径是目录/命名管道/设备/套接字等非普通文件），或内容不是一个完整的单证书（诊断信息写入标准错误，包含出错路径） |
| 2 | 用法错误：缺少检查路径、参数多余、命令未知（同时打印用法说明） |

失败时标准输出不会留下任何半截证书信息。

## 回归测试

构建后通过 CTest 运行（CTest 默认随构建启用；上面的普通构建已在构建树中备齐全部检查数据，直接执行即可）：

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

测试依赖均为系统上常见的公开工具：POSIX `sh`、coreutils（`base64`、`sha256sum`、`timeout`、`tr`、`sed`、`awk`、`cmp` 等）、`iconv`、`grep`；`read_socket` 一例只用 `python3` 标准库创建一个本地套接字节点。运行测试**不需要**安装 Python 的 `cryptography` 包，不需要联网，也不查询系统信任库。即使绕过构建步骤直接运行 `ctest`，也会先执行一次 `prepare_fixtures` 检查项在构建树中准备数据，任一 PEM 样本缺失、不可读或正文无法完整解码时该检查项失败并指明具体样本和原因，其余检查项不会带空 DER 或空指纹预期值继续运行。

### 证书样本的来源

测试证书样本只以 **PEM 形式**固定存放在 `tests/fixtures/` 并随仓库提交，有效期与序列号均为定值，不依赖联网或系统信任库。同一张证书的 DER 不作为二进制样本提交，而由 `tests/prepare_fixtures.sh` 在构建/测试时把对应 PEM 正文 Base64 **解码成完全相同的原始字节**得到：不生成新密钥、不重新签发，因此同一张证书的 PEM 与 DER 除 `Encoding` 外输出完全一致，预期指纹也始终来自这张原有证书（由测试脚本对解出的 DER 实时计算 SHA-256）。少数样本的某个字段无法用公开构建 API 表达，由 `tests/generate_fixtures.py` 在签名后对 DER 做定点改写——有效期标签（两位/四位年份、标签顺序、2 月 30 日）以及名称值的 BMPString/UniversalString 编码（含内容长度为奇数、非四字节整数倍的两个不完整名称值）都属此类；改写只动该字段的字节，重写后的签名在密码学上无效，但 `inspect` 本就不验证签名，且 prepare 解出的 DER 仍然逐字节等于该 PEM 的正文。`badsign.pem` 则是对 `valid` 证书只翻转签名 BIT STRING 末字节得到的完整证书：tbsCertificate（主体、颁发者、有效期、公钥、签名算法）逐字节不变，生成脚本用真实密码学断言原签名验证通过、篡改后验证失败，因此“签名失效”是输入真实具备的条件，而非以自签名、名称相同或过期代替。椭圆曲线样本同理：`ec_valid.pem` 携带一把 P-256 主体公钥，并由**另一把** P-256 密钥（`ec_issuer.pem` 的密钥）用 ECDSA 与 SHA-256 签发，主体与颁发者是两组固定的不同名称、有效期与序列号固定；`ec_issuer.pem` 本身是一张自签名 P-256 证书，作为颁发者公钥的固定载体随样本提交（叶子证书并非自签名，纯标准库证明需要从它取颁发者曲线点来验签）。`ec_badsign.pem` 是对 `ec_valid` 只翻转签名 BIT STRING 末字节（即 ECDSA 签名 DER SEQUENCE 中第二个 INTEGER `s` 的末字节）得到的完整证书：tbsCertificate 逐字节不变、签名 DER 长度不变，生成脚本用真实椭圆曲线密码学断言原签名在颁发者公钥下验证通过、篡改后验证失败，因此 EC 样本的“签名失效”同样是输入真实具备的条件。三张 EC 证书都只提交 PEM，DER 仍由 prepare 脚本离线从同一 PEM 正文逐字节解出。有效期写成不可能日期（2 月 30 日）的证书、以及名称字符串不完整的证书，其正文都照常解出 DER，由 `inspect` 继续识别为证书内容错误；而在单个 PEM 块正文中给完整证书追加零字节或第二张证书、以及只含密钥的异常输入根本不做解码、原样复制，继续触发原有的内容检查。

重新生成样本是**可选的维护操作**：在装有 Python `cryptography` 包的环境执行 `python3 tests/generate_fixtures.py` 可重写 PEM 样本（会更换密钥；该脚本只写 PEM，不写 DER），随后重新构建即可由 PEM 重新解出 DER，指纹预期值由测试脚本实时推导，无需手工同步。
